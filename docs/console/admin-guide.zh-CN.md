## 2. 上线前的设置

### 2.1 身份识别：先 observe，再 require

预算、档位上限和评估器的模板记忆，都只作用于**已验证身份**的调用。`observe` 模式下，不带有效 `x-api-key` 的请求照常服务，但不归属到任何人，也不受这些约束。

1. 先用 `observe`，让成员按"接入指南"配好各自的工具。
2. 在概览页确认"未归属"的比例接近 0。不为 0 时，在"路由决策"页按"未归属"调用方筛选，找出没带身份的工具。常见原因是 Claude Code 在 `apiKeyHelper` 之外还设置了 `ANTHROPIC_API_KEY`。
3. 切到 `require`。router 报告签名密钥已加载之前，控制台不允许切换。

不切到 `require` 也能用，但预算和档位上限只约束带身份的调用；评估器的模板记忆也不会工作（决策日志里没有 `templateChars`），学习式映射因此用不上模板长度。默认提示词包不依赖模板记忆。

### 2.2 路由方式：先观察，再自动

1. **只观察**：模型从不改变，控制台记录"自动"会怎么选。先跑一到两周，在"节省"页看"自动模式预估"，在"路由决策"页看评估器的意见是否合理。
2. **自动选模型**：确认无误后切换。是否同时打开"让 AI 判断每个任务的难度"（评估器 `auto`），取决于你对 fast 档的接受程度，见 [§6](#6-定期评估人工对比判断)。
3. 切换后一周内多看 [§3.1](#31-运行状况与成本) 和 [§3.2](#32-抽查路由决策)。

### 2.3 评估器

- **提示词包**：默认 `v2.3`。它在没有把握或没有规则命中时给出 standard，而不是不给意见；只在高置信度（≥ 0.9）时给 fast。没有新的离线评估结果时不要换包。
- **保留意见能沿用哪些档位**（部署参数，控制台里不能改）：一个 lineage 记住最近一次可用的评估器意见；之后某一轮没有新意见（跳过、超时、出错等）时，用保留的意见代替。默认只沿用 standard 和 frontier，**保留的 fast 意见不再沿用**，因为在真实会话里，被错误留在 fast 的轮次大多来自沿用。决策详情里"可沿用保留意见的档位"一行显示当前设置。部署时用 `-c assessorHoldTiers=standard,frontier`（默认）修改，`none` 表示完全不沿用，`fast,standard,frontier` 恢复旧行为。
- **学习式映射**（`mapping.learned`）是可选能力，默认包不带。只有在某个部署里有大量模板化的自动化流量、并且做过离线验证时才考虑。

### 2.4 把自动化 agent 接进来

定时任务、CI、批处理 agent 这类自动化流量，通常每次都带同一大段模板提示词，任务却很简单。这是 fast 档最能省钱的地方，但评估器在这类流量上往往认不出 fast（卡片的大部分被模板占满）。省钱的办法是 [§3.3](#33-建议的-fast-规则来自流量) 的模板族规则，**前提是这些 agent 的请求经过 router 且请求 `auto`**。如果它们直连模型或固定了模型名，控制台看不到它们，也就不会提出建议。

## 3. 每周的检查

### 3.1 运行状况与成本

- **运行状况**：5xx 比例、故障切换、router 开销和评估器延迟有没有上升；"Router 可用性信号"有没有告警；生效的配置版本是不是你最后启用的那个。
- **节省**：净节省 `N` 的趋势。注意它按目录价计算，不衡量质量（[使用说明 · 节省](README.zh-CN.md#节省)）。
- **用量与成本**：按档位分组，看 fast / standard / frontier 的占比有没有异常变化。frontier 占比突然升高，常见原因是新加了 frontier 规则，或某类请求触发了 prior-failures。

### 3.2 抽查路由决策

在"路由决策"页抽查十几条，重点看评估器给出意见的决策。打开决策详情，"评估器"一栏的代码说明依据：

| 代码（界面显示） | 含义 | 需要做什么 |
|---|---|---|
| 事实：没有其他依据 | 评估器有把握，但没有规则命中，按包的设置给 standard | 正常 |
| 事实：看不清任务 | 置信度低于阈值，给 standard | 正常；如果大量出现，说明卡片信息不够 |
| 未沿用保留的 fast 意见 | 本轮没有新意见，保留的 fast 意见被拦下，回落到默认档 | 正常（见 [§2.3](#23-评估器)） |
| 已阻止评估器降级 | 评估器想从不允许降级的档位往下降，被拦下 | 正常 |
| 事实：学习得到的映射 | 包里的学习式映射给出的档位 | 只在用了带学习头的包时出现 |

如果同一类任务反复被放到你认为不对的档位，记下几条决策 id，用于写规则（[§4](#4-写规则)）或下一次评估（[§6](#6-定期评估人工对比判断)）。

### 3.3 建议的 fast 规则（来自流量）

**位置**：路由策略 → 表单 → "规则"下方。

**原理**：使用同一模板（相同的工具列表和 system 提示）的请求构成一个**模板族**，router 在每次决策里记录它的 12 位指纹。控制台按天统计每个模板族的请求数、错误、故障切换、花费，以及评估器给出的任务事实，不保存任何内容。一个被咨询的 turn，如果评估器认为它**不改代码、此前没有失败、推理深度为 lookup 或 routine**，就算"代理判为 fast"（指标版本 `fast-proxy/1`）。一个模板族在窗口内满足下面两条时成为**候选**：

- turn 数 n ≥ 最少 turn 数（默认 30）；
- "代理判为 fast"比例的 Wilson 95% 下界 ≥ 最低下界（默认 0.95）。下界为 0.95 时，实际上至少需要约 73 个几乎全部判为 fast 的 turn，卡片上会算出这个数。

单个 turn 上这个代理指标很弱（在交互式会话上只有约一半准确），可靠性来自"很多 turn 都一致"加上人工审批。证据从记录模板族的 usage-ingest 版本开始积累，并且需要评估器在运行（observe 或 auto）；所以刚部署时表格是空的。

**审批步骤**：

1. 设好天数（默认 14）、最少 turn 数、最低下界，点"刷新"。
2. 找到状态为"候选"的模板族，看：
   - **请求占比**和**花费占比**：值不值得处理；
   - **assessor 档位**分布：评估器本身怎么看；
   - **健康状况**：错误和故障切换是否正常；
   - **样例决策**：点开几条"代理判为 fast"和"非 fast"的样例，确认它们确实是同一个 agent、同一类简单任务。
3. 点"添加规则"。编辑器里加入一条 `fast-family-<指纹前 8 位>`：这个模板族 → fast，状态显示"在本次编辑中（未激活）"。
4. 保存草稿 → 校验 → 启用。启用说明里已预填证据（规则 id、指标版本、n、下界、时间窗），可以补充你的理由。

**审批前想清楚两点**：

- 规则对**所有调用方**的同一模板族生效。另一个团队如果用完全相同的工具列表和 system 提示，也会走 fast。样例里的调用方是不是你预期的那些？
- 规则优先于评估器。生效后这个模板族**不再咨询评估器**（没有延迟、不花钱），所以它的代理证据停在启用时的状态。
- Claude Code 的模板族从 2026-11-20 的版本起不再包含它 system 开头那行计费头（`x-anthropic-billing-header`，后缀随对话而变）。所以 Claude Code 的模板族指纹在那次升级时整体换了一次，之前的证据和按旧指纹写的规则不再匹配；其他客户端不受影响。

**生效后的监控**：状态变为"规则已生效"，卡片改为显示健康状况：错误、故障切换、提示次数，以及用户 turn 实际在各档位服务的数量。出现下面情况时考虑撤销：

- 这个模板族的错误或故障切换明显上升；
- 用户或 agent 反馈结果变差；
- 这个 agent 的任务类型变了（例如从整理摘要变成改代码），而模板没变。

**撤销**：点"移除规则"（或在规则列表里删除），保存草稿 → 校验 → 启用。

## 4. 写规则

### 4.1 规则怎么生效

- 从上到下，第一条所有条件都满足的规则决定这个请求的档位，**优先于评估器**；命中规则的请求不咨询评估器。
- 规则只对请求 `auto` 的调用生效，不影响 `auto:fast` 这类别名和指定了模型名的请求。
- 条件有：会话类型（主会话 / 子 agent）、提示词长度上下限、请求的模型名、agent id、模板指纹，以及客户端在请求里声明的**权限模式**和**推理强度**。
- "用一句话描述规则"可以把自然语言翻译成规则（会调用部署配置的规则模型，并显示费用）；加入草稿之前不会生效。句子里按任务内容判断的部分（例如"做动画或视觉设计"）路由规则表达不了，会变成一条建议的管理员规则（[§4.3](#43-管理员规则按任务内容判断)），以观察状态加入。
- 路由规则只看确定性的条件，判断快、不花钱、结果可复现。想按"任务是什么"定档，用评估器的管理员规则。

### 4.2 常用规则

| 目的 | 规则 | 注意 |
|---|---|---|
| 某个自动化 agent 走 fast | 模板指纹 = 它的模板族 → fast | 优先用 [§3.3](#33-建议的-fast-规则来自流量) 的建议，有证据 |
| 用户在规划时用最强模型 | 权限模式是 `plan` → frontier | 只有 `plan` 和 `auto` 可识别；default、acceptEdits、bypassPermissions、dontAsk 模式不发送这个字段 |
| 用户显式要求最高推理强度时用最强模型 | 推理强度是 `max` 或 `xhigh` → frontier | Claude Code 每个请求都带推理强度，默认 `high`，所以 `high` 没有区分意义；Codex 只在用户设置时发送 |
| 用户显式要低推理强度时省钱 | 推理强度是 `low` → fast | 同上 |
| 子 agent 从便宜的档位开始 | 会话类型 = 子 agent → fast | 子 agent 的第一步多是探索性读文件；不确定时先在只观察模式下看效果 |

关于 frontier 规则：在我们的编程 agent 基准上，frontier 做对的任务并不比 standard 多，成本却高 2.5–6 倍（[结论总结](../experiments/harbor-summary.zh-CN.md)）。把 frontier 留给你确认需要的场景，并在"用量与成本"里留意 frontier 占比。

### 4.3 管理员规则（按任务内容判断）

管理员规则是写给评估器的自然语言规则，例如"做动画、视频或以视觉效果为主的 UI 设计 → 很难（frontier）"。它和评估器内置的规则在**同一次调用**里判断，不多花一次调用；没有被路由规则命中、而且咨询了评估器的请求才会用到它。

**预置规则**：代码里预置了一条 `x-visual-creative`（动画、视频或以视觉效果为主的 UI 设计 → frontier），默认是观察状态。新部署的内置配置（评估器开启时）带着它；在控制台把评估器从关闭（或未设置）打开时也会加上它，除非关闭前的评估器设置里已经有自己的管理员规则列表。已有的配置文档不会自动获得它：在"评估器 → 管理员规则"里点"加入预置规则"，或启用一个带它的版本。配置文档里没有 `customRules` 就是没有管理员规则。

**怎么写**（评估器 → 管理员规则 → 添加管理员规则）：

- 最多 5 条。id 是 `x-` 加小写字母、数字或连字符。
- "什么情况下命中"用**英文写一行**（≤ 600 字符），描述任务本身，例如 `The user asks to build or polish an animation, a video, or a visually designed UI (look and feel is the main goal). Judge the session's task, including the first user message. Not for small style tweaks such as changing one colour.`
- 评估器只看任务卡片（最新和首条用户消息、上一轮的片段、工具名和统计），看不到文件内容。规则要写成卡片上能判断出来的样子。
- 想让会话里的后续轮次（"颜色再调暖一点"）也命中，就在规则里写明按会话的任务判断、包括首条用户消息。
- 排除小改动，否则会和内置的 fast 规则冲突（冲突时这一轮没有意见，沿用会话上一次的判断）。

**先观察，再开启**：

1. 新规则是"观察（只记录）"状态：每次咨询都判断并记录是否命中，但不改变档位。证据表里的"效果"列显示开启后会改变哪些轮次（"开启后会改变：…"）。
2. 看"管理员规则的证据"：判断次数、命中率（95% 区间）、命中时的服务档位、健康状况，并点开样例决策看命中的是不是你想要的任务。样本太少（几十次以下）时区间很宽，多等几天。
3. 满意后点"开启"切到"生效"，照常校验 → 启用。启用说明里会自动带上证据。
4. 生效后看"之后的轮次低于规则档位"：命中之后的下一次判断被服务在更低档位的比例。默认的降档保护不允许评估器把 frontier 会话往下降，所以 frontier 规则的这一列通常接近 0。评估器或路由不在自动模式时，这一列没有意义（页面会提示）。

**要知道的事**：

- 只有评估器处于自动模式、路由方式是"自动选模型"时，"生效"的规则才会改变模型。评估器只记录时，规则照样被判断和记录。
- **子 agent 不会被管理员规则提高档位**（省钱优先）；命中照样记录。
- **评估器没把握时，生效的规则照样算数。** 评估器对整体判断的置信度低于阈值（默认 0.8）时，内置规则不再算数，只给"看不清任务"的 standard；但命中的"生效"状态的 frontier 或 standard 管理员规则仍按它的档位给出。这也意味着没把握时的误判会把请求升到 frontier，开启前先在证据表里看看样例。同时命中内置的 fast 规则时仍按冲突处理；fast 管理员规则没有这一例外。
- 新增、修改、开启或关闭规则后，正在进行的会话会在当前轮重新咨询一次评估器，之前沿用的判断作废。
- 修改规则的说明或档位后，这条规则的证据从头开始积累；旧文本的证据仍在表里，标为"旧文本"。
- 费用：每条规则让每次咨询多约 100–150 个可缓存的提示 token 和 30–50 个输出 token。
- 规则的说明会发给评估器模型；不要写进机密信息。决策日志里只有规则 id，不记录任务内容或判断理由。

## 5. 改动的安全流程

所有路由相关的改动（规则、模型池、评估器、模式）都走同一流程：

1. **草稿**：在表单或 JSON 页签里修改，保存草稿。
2. **校验**：用 router 自己的校验逻辑检查；有错误时不能启用。
3. **启用**：写说明。对话框会用句子显示改动前后的效果。router 约 1 分钟内加载新版本；进行中的会话保持当前模型，直到下一个缓存断点。
4. **观察**：启用后看一天的运行状况和路由决策。
5. **回滚**：在"版本"里选之前的版本回滚，这会用旧内容创建一个新版本；审计日志保留所有记录。

一次只改一件事，便于判断效果。

## 6. 定期评估：人工对比判断

评估器和规则好不好，最终要看"用更便宜的档位，结果是否同样可以接受"。这件事目前只有人能可靠判断：

- 不看输出、凭印象给档位，人往往偏高（在我们的标注里，只有 2% 的轮次被标为 fast）。
- 看到 fast 和 standard 给出的**真实下一步**后，同一个人在 76% 的轮次上认可了 fast。
- 用 LLM 当裁判，总体比例接近，但逐轮和人的判断几乎不一致（κ 0.14）；只比较第一步的反事实标签，在多步任务上主要反映"第一步是不是一样"。

所以建议每 1–3 个月，由负责路由的人做一次人工对比判断，用结果决定：要不要多用 fast（例如打开评估器 `auto`、加 fast 规则），还是保持现状。做法（需要仓库和本地的 Claude Code 会话记录）：

1. 用 `experiments/assessor-v24/heldout.py` 导出上次评估之后的新会话（与以往评估的会话不重叠），积累到几百轮。
2. 为抽样的轮次生成 fast 和 standard 的下一步（有费用，先确定预算上限）。
3. 用 `python3 human.py compare` 逐轮判断 A、B 两个下一步哪个更好或一样好（A/B 顺序随机，看不到哪个是 fast）。
4. 用 `agree.py` 汇总：按任务类型和长度，看 fast 的可接受比例；用效用指标（⑦）比较提示词包或设置。

方法和上一次的数字见 [评估器 v2.4 报告](../experiments/assessor-v2.4.zh-CN.md)。

## 7. 排障速查

| 现象 | 先看哪里 | 常见原因与处理 |
|---|---|---|
| "建议的 fast 规则"一直是空的 | 表格摘要行 | 刚部署，证据还在积累；评估器关闭了（要 observe 或 auto）；自动化流量没经过 router 或没请求 `auto`（[§2.4](#24-把自动化-agent-接进来)） |
| 都是"未达门槛" | n 和下界两列 | 流量不够，或这个模板族确实不简单；可以加长天数窗口，但不建议随便降低下界 |
| 某个模板族规则生效后错误上升 | 卡片健康状况、路由决策 | 撤销规则（[§3.3](#33-建议的-fast-规则来自流量)），看样例里失败的请求 |
| frontier 花费突然升高 | 用量与成本（按档位）、版本 | 新加的 frontier 规则（例如推理强度、权限模式）命中面太大；收窄条件或回滚 |
| 规则写了但不生效 | 路由决策里的依据 | 请求不是 `auto`；上面有另一条规则先命中；条件值和客户端发送的不一致（推理强度、权限模式只按客户端实际发送的值匹配） |
| 决策日志里一直没有 `templateChars` | 设置 → 部署 | 身份识别还是 `observe`，模板记忆只对已验证调用方工作（[§2.1](#21-身份识别先-observe再-require)） |
| 评估器延迟或超时增多 | 运行状况 | 上游模型变慢；超时的轮次没有新意见，回落到默认档或保留的 standard / frontier 意见，不会因此走 fast |
