# 评估器提示包 v2.3：在真实会话上校准 tier 判断（评估报告）

> 本报告的数字来自 `experiments/assessor-v23/`。评估计划（数据、切分、标签、指标）在任何留出集调用之前写在
> `experiments/assessor-v23/PREREG.md`；最终的包在留出集调用之前冻结（`FROZEN.json`）。数据来自本机的 Claude Code
> 会话记录，只在本地使用（`results/` 不提交）。本报告只有汇总数字，不引用任何会话文本。

## 摘要

**问题。** v2.2 在 Harbor 基准上和固定 Sol 一样，但这些基准只看会话开始时的一张 card。真实的交互会话里，大多数
咨询发生在后续的用户 turn 上。这些 turn 上 v2.2 表现如何，能不能改进？

**做法。** 从 294 个本机 Claude Code 会话中导出 1,382 个用户 turn。由两个强模型（Opus 5.5、GPT Astra）事后打标签：
它们能看到请求本身，以及 agent 随后实际做了什么。按会话 50/50 切分，所有选择只在 dev 上做，留出集只跑一次。

**结论（留出集，524 个两位标注者一致的 turn，v2.3 对 v2.2）：**

| 指标 | v2.2 | v2.3 | 差（95% CI，按会话 bootstrap） |
|---|---|---|---|
| 被错误留在 fast 的 turn | 14.1% | 2.3% | **−11.8 pp [−18.7, −4.9]** |
| 服务档低于需要（质量风险） | 24.6% | 17.7% | **−6.9 pp [−12.4, −0.8]** |
| 服务档与标签一致 | 54.6% | 57.4% | +2.9 pp [−4.1, +8.5]（未检出差异） |
| fast 判断的精确率 | 75.6%（41 次） | 76.2%（42 次） | 不变 |
| 给出意见的比例 | 33% | 98% | |
| 档位价格指数（相对全部 standard） | 0.80 | 0.93 | +0.13 [+0.05, +0.21]；按标签的应付值是 0.87 |

1. **v2.2 的主要问题不在判断本身，而在"无意见"。** v2.2 在真实 turn 上 66% 的咨询是 `low-confidence` 或 `no-rule`。
   core 在没有意见的 turn 上沿用 lineage 保留下来的上一个意见（task 11-16 D2），于是一次 fast 判断会一路带进后面
   并不是 fast 的 turn。这就是留出集上 14.1% "被错误留在 fast" 的来源：74 个这样的 turn 里，64 个是沿用保留的意见，只有 10 个来自当轮错误的 fast 判断。
2. **v2.3 用三项映射改动修掉了这个问题**：看过但不能判 fast 的 turn 明确给 standard；看不清任务时也给 standard；
   fast 要求置信度 ≥ 0.9。同时改用 `card/v2`，带上一轮的上下文。在四种标签定义下（只看 Opus、只看 Astra、两者取低、
   两者取高），"被错误留在 fast" 和 "服务档偏低" 的下降都成立，区间都不含 0。
3. **代价是成本指数上升**：v2.2 便宜，有一部分是因为把该用 standard 的 turn 留在了 fast 上。v2.3 的成本指数 0.93
   比按标签的应付值 0.87 略高，v2.2 的 0.80 则低于应付值。
4. **整体判对率没有检出提升。** 剩下的误差主要是 fast 认不出来（召回约 20%）和 frontier 认不出来（召回约 4%）。
   这两项都试过的办法（更强的模型、提示词改动）都没有成功，见第 4 节。
5. **没有回归。** 旧的评估集上 fast 精确率保持 100%，SWE-bench 整体判对率从 86.9% 提高到 95.3%。Harbor 两个基准上
   与 v2.2 相同：全部判 standard，质量 0.0 pp，成本 ×1.02–1.07，区间含 1.00。

6. **第二个留出集（自动化 agent，1,490 个 turn）上 v2.3 与 v2.2 持平**，判对率 −0.7 pp [−2.7, +0.9]。这类流量的问题是 fast
   几乎认不出来，召回约 5%。按 template family 的确定性 policy 规则在 dev 上选出、在 test 上检验：规则决定了 93% 的 turn，
   精确率 97.5%，判对率从 8.8% 升到 93.8%。交互式会话上没有任何 family 达到门槛（4.6）。
7. **三个映射键在留出集上逐项消融，各自都显著降低了"被错误留在 fast"和"服务档偏低"**（4.4）。0.9 的置信度门槛挡下的
   fast 只有 58% 真是 fast。

v2.3 已设为代码默认（`defaultPackName`、router 和 infra 的默认值）。所有规则仍是 `auto: false`，没有部署。

## 1. 数据与标签

### 1.1 会话 turn

`sessions.py` 从本机 `~/.claude/projects/` 中与开发相关的项目目录里导出每一个由模型回答的用户文本消息（排除
另一个自动化工作区的定时任务会话）。每条记录包含两部分：

- 构造 card 用的字段：最新消息、首条消息、上一条用户消息、agent 上一轮回复的结尾、上一轮工具调用和错误数、system
  开头、工具名、turn 序号、压缩次数；
- 事后摘要，只给标注者看：随后的工具调用序列（工具名和参数摘要）、改了哪些文件、出错次数、最终回复的开头和结尾、
  用户下一条消息的开头。

| 类别 | 说明 | dev | test |
|---|---|---|---|
| human | 用户写的消息 | 317 | 277 |
| notification | 客户端插入的通知（后台任务、子 agent 完成） | 337 | 147 |
| subagent | 子 agent 收到的委派任务（不含 fork） | 104 | 122 |
| compaction | 上下文压缩后的续接摘要 | 33 | 24 |
| command | slash 命令 | 10 | 11 |
| 合计 | 294 个会话，10 个项目 | 801（139 个会话） | 581（155 个会话） |

真实消息很短：human 消息的中位长度是 40 个字符，常见的是"可以，做吧""用第二个方案""ok"这类。card/v1 没有 agent 上一轮说了什么，
这类消息无从判断。

### 1.2 标签

`judge.ts` 让两个不同家族的强模型分别给每个 turn 打 fast / standard / frontier。它们看到请求和事后摘要，判断"这一轮
的工作实际需要哪一档"。

- 两位标注者一致率 89.2%，κ = 0.82（1,382 个 turn）。主要标签取两者一致的 turn（dev 709，test 524）。敏感性分析用
  只看一方、两者取低、两者取高。
- 标签与实际工作量相符：fast 标签的 turn 中位 2 次工具调用、3% 有编辑；standard 10 次、28%；frontier 52 次、74%。
- 标签在任何候选包出现之前就已全部生成。

**标签不是实测结果。** 它们是看过结果之后的判断，不是"换成 fast 模型实际会不会失败"的测量。Harbor 实验测到的是：
在基准任务上 frontier 并不比 standard 解决得更多。所以这次没有按标签去放宽 frontier，frontier 的数字只报告。

### 1.3 怎么算服务档

每个 turn 由 assessor 给出意见或无意见。服务档按 core 的规则：有意见用意见；没有意见时沿用同一会话（子 agent 则是
同一 lineage）上一次的意见；都没有就用 pool 默认（standard）。不模拟成本门和降级保护，只评估 assessor 本身。card
由生产代码 `buildCard` 从重建的 Messages 请求体构造。

## 2. v2.3 改了什么

### 2.1 card/v2

| 字段 | 内容 | 上限 |
|---|---|---|
| `prevUser` | 最新一条之前的用户消息（它就是首条时省略） | 600 字符 |
| `prevAssistant` | 最新用户消息之前、上一轮 agent 最后一段文字回复的结尾 | 800 字符（保留结尾） |
| `stats.prevTurnToolErrors` | OpenAI 两种格式没有错误标志：读取工具输出开头的退出码（Codex 的 `Process exited with code N`） | — |

pack 在 `pack.json` 的 `card` 里声明版本；`card/v1` 的内容不变；`card/v2` 只增加可选字段，所以 card/v1 仍可交给 v2 的 pack，
反过来会被拒绝。

### 2.2 映射（`pack.json` 的 `mapping` 块，三个新键，不写就和以前一样）

| 键 | v2.3 的值 | 效果 |
|---|---|---|
| `unmatchedTier` | `standard` | 置信度够但没有成立的 fast、也没有其他规则或事实时：standard（`fact:unmatched`），不再是 `no-rule` / `fast-unsettled` |
| `lowConfidenceTier` | `standard` | 置信度低于阈值时：standard（`fact:low-confidence`），不再是无意见 |
| `fastMinConfidence` | 0.9 | fast 规则成立还要求置信度 ≥ 0.9；不满足时按 `unmatchedTier` 处理 |

仍然是无意见的只剩：precheck 跳过（"ok""continue"这类，沿用保留的意见是对的）、fast 与 frontier 冲突、调用失败或超时。
router 对带 `lowConfidenceTier` 的 pack 把 core 的最低置信度设为 0，因为 pack 已经自己按阈值处理过；其他 pack 不变。

### 2.3 提示词

规则、示例的输出与 v2.2 完全相同；指令只多了两个新字段的说明（有测试锁定）。示例的 card 改成 `card/v2`。

### 2.4 日志

router 的 `assessor` 记录增加 `matched`（模型判为命中的规则 id）和 `facts`（五项事实，只有枚举值、布尔和计数），
usage-ingest 原样存入记录。以前只有 `basis` 和 `outcome`，`no-rule` 的成因无从查起，也没法给 observe 记录打标签。

## 3. 开发集上的选择（dev，709 个一致标签）

只在 dev 上看，比较的都是同一批 turn。

| 候选 | 改动 | 判对率 | 被错误留在 fast | fast 次数 / 精确率 | 结论 |
|---|---|---|---|---|---|
| v2.2 | — | 48.1% | 20.2% | 43 / 60% | 基线 |
| m | card/v2 + `unmatchedTier` | 53.0% | 7.5% | 63 / 68% | 判对率 +4.9 pp [+0.7, +7.4]，保留 |
| a | m + 跟进类和通知类指引 + 4 个示例 | 52.4% | 24.9% | 185 / 58% | 通知类 turn 大量误判 fast，否决 |
| a（Haiku 5.5 作 assessor） | 同 a | 48.9% | 35.9% | 207 / 57% | 更差、p50 延迟 2.7 s，否决 |
| a-r / b / b-r | 规则措辞、去掉通知指引 | 53.5–54.7%* | 1.8–3.0%* | — | 与 m（54.4%*）持平，没有一个胜过 m |

\* 带最终映射（`lowConfidenceTier` 和 `fastMinConfidence` 0.9）。同样的映射下 m 为 54.4%，d 与 m 的差 +0.4 pp [−1.6, +2.4]。

另外两项在 dev 上检查、没有采用：

- **通知类 turn 不咨询**（沿用上一个意见）：判对率 52.5%，低于咨询的 54.4%。
- **换更强的 assessor 模型**（GPT Sol，effort low，用 b-r）：fast 精确率 100%，但 fast 次数降到 16 次，整体判对率与 Luna
  相同（−0.4 pp [−1.6, +1.6]）。每次 $0.018，是 Luna 的 23 倍；p50 3.0 s。只看 card，换模型提高不了召回。

### 4.4 逐项消融（冻结后的留出集调用，不重新调用模型）

`ablate.py` 用每次调用记录下的事实、命中规则和置信度，在冻结的 v2.3 结果上逐一去掉一个映射键重算：

| 去掉 | 判对率 | 被错误留在 fast | 服务档偏低 | 去掉后 fast 次数 / 精确率 |
|---|---|---|---|---|
| （冻结的 v2.3） | 57.4% | 2.3% | 17.7% | 42 / 76.2% |
| `fastMinConfidence` | 58.2%（差 −0.8 [−2.5, +0.5]） | 3.8%（−1.5 [−2.9, −0.3]） | 19.1%（−1.3 [−2.5, −0.3]） | 61 / 70.5% |
| `lowConfidenceTier` | 57.4%（0.0 [−0.8, +0.7]） | 5.0%（−2.7 [−4.0, −1.4]） | 19.1%（−1.3 [−2.3, −0.5]） | 42 / 76.2% |
| `unmatchedTier` | 57.3%（+0.2 [−1.3, +1.4]） | 4.2%（−1.9 [−3.6, −0.2]） | 19.5%（−1.7 [−3.2, −0.2]） | 42 / 76.2% |

括号里是"冻结的 v2.3 减去去掉该键后"的差。三个键在留出集上各自都显著降低了"被错误留在 fast"和"服务档偏低"，
都不改变判对率。0.9 的置信度门槛挡下了 19 次 fast，其中标签为 fast 的只有 58% [36, 77]，低于留下的 fast 判断的
76%。这个门槛是在 dev 上选的，留出集上的消融支持它，不是只在 dev 上成立。

### 4.5 第二个留出集：自动化 agent 的会话

`PREREG.md` 的补充说明在调用之前写好：主导出排除的那个自动化 agent 工作区，共 1,601 个 turn、1,485 个会话，来自另一种
客户端，大多是固定模板的辅助 agent（命名、打标签、归档、记忆整理）。没有在它上面调过任何东西，同样两位标注者打标签
（一致率 93%，κ 0.48：几乎全是 fast，κ 因此偏低），v2.2 和冻结的 v2.3 各跑一次。

| 指标（1,490 个一致标签，96% 是 fast） | v2.2 | v2.3 | 差（95% CI） |
|---|---|---|---|
| 服务档与标签一致 | 9.9% | 9.1% | −0.7 pp [−2.7, +0.9] |
| 被错误留在 fast | 0.9% | 0.1% | −0.8 pp [−1.8, 0.0]（主口径区间上界为 0；其余四种标签口径的区间都不含 0） |
| fast 精确率 / 召回 | 97.1% / 4.6% | 97.8% / 6.1% | |

v2.3 在这里既没有变好也没有变差。两个版本都只认出约 5% 的 fast turn：这些请求把很长的 agent 说明放在用户消息开头，
card 截取的前 4,000 个字符几乎全是说明，模型看不到具体任务，于是给出低置信度或"没有依据"。

### 4.6 确定性的 fast 规则（policy 规则）

最初的方向之一是不经过 LLM，用 policy 规则直接给 fast。core 的规则可以匹配 lineage 类型、template family（工具集 +
system 的哈希，router 每次决策都记录）、agent id 和 prompt 大小，而且优先于 assessor 的意见。`family_rules.py` 按 template
family 分组，在 dev 上选出"至少 30 个标签、fast 比例的 Wilson 下界 ≥ 95%"的 family，生成 `templateFamily → fast` 规则，
再在 test 上检验。

| 数据 | dev 上合格的 family | test 上规则决定的 turn | 其中 fast | test 判对率（v2.3 → v2.3 + 规则） | 被错误留在 fast | 价格指数（应付 0.09） |
|---|---|---|---|---|---|---|
| 交互会话 | 0 / 51 | 0 | — | 不变 | 不变 | 不变 |
| 自动化 agent | 1 / 10 | 676 / 727 | 97.5% [96.0, 98.4] | 8.8% → 93.8% | 0.0% → 2.3% | 0.95 → 0.10 |

相对 v2.2，v2.3 + 规则在自动化 agent 的 test 上判对率 +83.4 pp [+73.7, +90.7]，价格指数 −0.83 [−0.90, −0.74]，被错误留在 fast
+1.9 pp [+0.9, +3.0]。

结论：

- **固定模板的辅助 agent**：确定性规则有效，而且远比 assessor 有效，因为任务就是模板本身。不需要代码改动：core 的
  `templateFamily` 规则早就支持，用 `family_rules.py` 的方法在 observe 记录上选 family 即可。注意这里的 family 是用会话
  记录里能拿到的工具名和 system 开头构造的近似值，部署时要用 router 日志里真实的 `templateFamily`，并用部署自己的
  标签重新选择。
- **交互式会话**：没有任何 family、子 agent 类型（152 个子 agent turn 里只有 1 个 fast）、工具集（Claude Code 总带写工具）、
  消息类型（human、通知的 fast 比例都在 34%–53%）或 prompt 大小达到门槛，所以不加规则。
- 反方向有一个信号：slash 命令（约 90% frontier，各约 10 个）和压缩后的续接（约 56% frontier）。Harbor 的实测没有显示
  frontier 比 standard 解决得更多，所以没有据此加 frontier 规则。

### 4.7 延迟与成本

每次咨询 p50 1.30 s、p95 1.57 s（v2.2：1.27 s / 1.49 s）；$0.00077（v2.2：$0.00072）。card/v2 的中位长度比 v1 多约 800 字符。

## 5. 对部署的含义

- **observe 模式下**，v2.3 让日志里几乎每次咨询都有 `proposedTier`，并带上 `matched` 和 `facts`。下一步按真实流量
  统计 fast 精确率、放开 auto，就有了数据基础。
- **auto 模式 + `AUTO_RULES=all`**：最大的变化是看不清或无规则可依的 turn 不再沿用保留的 fast 意见，这正是 4.1 中
  human turn 上"被错误留在 fast"从 23.9% 降到 3.5% 的来源。`AUTO_RULES=pack` 下所有规则仍是 `auto: false`，行为不变。
- **补充（2026-11-17，只用 dev 集）：保留的 fast 意见不再沿用。** v2.3 之后仍会沿用 fast 的只有 precheck 跳过、冲突和
  调用失败。core 的 `assessorHoldTiers` 默认改为 standard 和 frontier（[assessor 设计 §2.4](../architecture/assessor-design.zh-CN.md#24-意见怎么用)）。
  `hold.py` 在 dev 集上模拟：v2.3 下被错误留在 fast 2.7% → 2.4%，价格指数 0.931 → 0.934（+0.003），只涉及 2 个 turn；
  v2.2 下 20.3% → 2.4%，价格指数 0.749 → 1.047。没有在留出集上评分（留出集已用过一次）。
- **没有部署。** us-west-2 的 router 仍是部署时的镜像和配置文档（文档里写明了 pack）。重新部署后，新的 baked 默认值
  才是 v2.3。如果要保持 v2.2，需要在配置里显式选择它。

## 6. 局限

- **标签来自 LLM 的事后判断**，不是 fast 模型实际跑出来的结果。两位标注者来自不同家族、一致率 89%，但它们可能有
  共同的偏好。
- **会话来自同一位用户的本机记录**：交互会话以 Claude Code 为主（10 个项目，294 个会话），加上一个自动化 agent 工作区。Codex 类客户端的 turn 没有覆盖：
  card/v2 读取退出码只由单元测试验证，没有真实会话数据。
- **card 是重建的**：system 开头和工具名取自会话记录里的请求形状，其余字段取自会话记录，不是 router 实际收到的请求体。
  router 侧由集成测试保证 card/v2 的构造与发送。
- **服务档的模拟不含成本门、次数门和降级保护**，只评估 assessor 的意见本身。
- **fast 和 frontier 的召回仍然很低**（约 20% 和 4%）。只看一张 card，换更强的模型也没有提高。固定模板的流量可以用 template family 规则解决，交互会话找不到这样的信号（4.6）。
- **主指标"判对率"在留出集上没有检出提升**（+2.9 pp，区间含 0）。被证实的效果是"被错误留在 fast"和"服务档偏低"这两项质量风险指标。
- 留出集用过一次；以后再改 pack 需要新的留出数据，例如 observe 记录配合 `matched` / `facts` 打标签。
